# Feedback and project memory

A comment belongs to a particular version and timecode. Record the original wording, intended change, protected context, status and evidence. Use open → applied → verified; accepted means explicit author acceptance. A rejected version remains rejected until a new change is reviewed. Cancelled means the task was withdrawn. Keep review status separate from queue membership: applied or verified is still unaccepted, but historical unaccepted notes are not automatically new assignments. Store active/archived queue state and the reason for archiving without overwriting the original status.

Reusable preferences belong in preferences.json, with scope and rationale. Shot-specific removal, travel facts and one-off duration constraints stay in the scene/feedback. Written instructions do not fix a timeline. A good idea does not establish acceptance of the resulting edit.

Before a change, save the current version. After it, inspect the changed section and adjacent context, and compare protected tracks. Export one clearly named review version. Replay is optional; a local feedback file works. Never close external comments automatically merely because a script succeeded.

Update STATUS.md with current version, source/export identities, actual coverage, unresolved issues and next step. When handing off, confirm the destination has the project export and required media; a shared folder or saved chat alone does not prove delivery. Only one writer changes the same Resolve project at a time. Confirm live ownership before editing; an old status file does not prove another agent is still active. Reviewers produce separate reports and the editor integrates them.

Keep originals and selected music/voice media on the designated media drive, editor databases/cache locally outside cloud sync, and documents/review copies/versioned project exports in shared storage. Check paths and media access on each computer; do not move or rename originals to enforce a folder scheme. A DRP contains a project, not its camera media. A shared drive is not a write lock. Before handoff, save/export/verify the project, update status, confirm sync at the destination and recheck media paths there. Documentation-only work needs no Resolve export.

Status records an ISO timestamp with timezone, operator/computer role, exact version, completed work and evidence, remaining work, active processes, next step and any genuinely required answer. Keep current and previous entries readable and move older entries to a dated archive. Keep credentials, active databases and temporary environments out of synchronized project documents.

## Turn verified lessons into a reusable workflow

Record the symptom, intended result, cause supported by evidence, actual correction, protected material, verification method and remaining limit. Keep the original words, but distinguish their intent from literal examples. A request for short, varied shots does not prescribe a universal duration, and a desired direction does not ban purposeful reframing.

Route each lesson once: a shot-specific decision to scene feedback, reusable taste with its scope to preferences, a reliable procedure to the relevant workflow reference, and an unsuccessful experiment to a historical report with a reason not to reuse it. Update the relevant entrypoint so the procedure can be found; avoid duplicating the whole conversation or leaving contradictory active rules.

When preparing an authorized public skill update, maintain a trace from the private lesson to the generic rule and its validation. Keep family identities, source media, local paths, licensed assets, private speech and provider credentials out of the public patch. Preserve preferences as scoped choices rather than universal rules. Record whether an improvement is local only, prepared, submitted or released; a public draft is not an installed release. Publish only within the user's request and follow the repository's contribution/release process.
